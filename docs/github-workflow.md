# Building and releasing from a GitHub workflow

> **Untested in studio production.** This page and its workflow are an example to adapt. They show
> one way to automate the steps in [Deployment](deployment.md) and [Releasing](releasing.md). We
> haven't run them in a studio's production pipeline, so test them against a copy of your stores
> first.

You want new Griptape Nodes releases built and released the same way every time, with a person
approving before anything reaches artists. A GitHub Actions workflow can do that.

The example is
[`examples/github-workflow/build-and-release.yml`](../examples/github-workflow/build-and-release.yml).

## What the workflow does

It runs three jobs, one after another:

1. **Build.** On each platform in turn, build the engine and the library into the local store.
2. **Launch package.** Write the launch package and check it resolves.
3. **Release.** After someone approves, copy the tested packages to the release store with
   `rez cp`.

Someone starts it from the repository's **Actions** tab, with the engine version and library to
build.

## Why release with `rez cp`?

Because the packages are already built and checked. Releasing only copies them.

`rez cp` copies a package with its payload and every variant, exactly as it is in the local store.
What artists get is what you tested. Nothing is rebuilt between testing and production.

`rez release` builds a package from its source and installs the result. That suits a package whose
source lives in the repository. These packages are generated by the build tool, so there is nothing
for `rez release` to build.

The release job calls [`examples/release_family.sh`](../examples/release_family.sh), or
[`examples/release_family.ps1`](../examples/release_family.ps1) on Windows. Both follow
[Releasing](releasing.md): copy what the family resolves from the local store, skip what's already
released, then check it resolves without the local store.

## Before you start

- **Self-hosted runners** on each platform you support, with Rez, uv, and Python 3.12. GitHub's
  own runners can't reach your stores. Windows runners need PowerShell 7 (`pwsh`), not bash.
- **Your stores mounted** on every runner, at the paths the workflow uses.
- **A `rez` label** on those runners, alongside `Linux`, `Windows`, or `macOS`.
- **An environment named `rez-release`** in the repository settings, with required reviewers. The
  release job waits there until one of them approves.

## Adapt the example

Change these before the first run:

- The store paths and Rez tools folders in each job's `matrix`.
- `production_paths`: the search path artists use, without the local store. Separate entries with
  `:`, or `;` on Windows.
- `BUILD_TOOL`: pin it to a commit you've tested, instead of `main`.
- The release job's `actions/checkout` of this repository: pin its `ref` the same way.
- The platforms. Remove the matrix entries for any you don't support.

## Why it runs one platform at a time

Two builds writing the same package at once can lose a variant (see
[One store, several platforms](deployment.md#4-one-store-several-platforms)).

The workflow guards against that twice. `max-parallel: 1` runs the platforms one after another.
The `concurrency` group stops a second run from starting while one is still writing.

## Torch builds

Enter the torch builds in the `torch_backends` input, for example `cpu cu128`. Name each build:
`all` works for `build-library` on its own, but the workflow rejects it, because the release copies
each named build and there is no build called `all`.

Linux and Windows build each one, and the release copies each one. macOS has a single torch build
and skips this.

Choosing a build for each artist's machine stays outside the workflow. Run
`griptape-nodes-rez gpu-config` on each machine, as in [GPU builds per machine](gpu-builds.md).

## How studios run Rez from CI

Public examples are rare, but the ones we found share a shape:

- [One Animation](https://github.com/oneanimation-rnd/github/blob/main/.github/workflows/rez-release.yml)
  keeps a reusable workflow that runs `rez release` on a self-hosted Linux runner. Each package
  repository calls it.
- [UTS Animal Logic Academy](https://github.com/UTS-AnimalLogicAcademy/open-source-rez-packages)
  keeps a `rez-release.sh` script next to each open-source package it builds, such as USD and OCIO.

Both build from source with `rez release`, because their repositories hold the source. Here the
build tool makes the packages, so the release step copies them instead. Both use self-hosted
runners or machines that can reach the studio's stores, as this example does.

## Good to know

- The build tool never changes your Rez configuration. Each command checks what it wrote, and a
  failed check fails the job.
- The workflow doesn't run `gpu-config` or change artists' machines.
- A failed build or release can be run again. Built packages of the same version are kept, and
  already released versions are skipped.
- To release packages you built by hand, run the release script yourself, as in [Releasing](releasing.md).
